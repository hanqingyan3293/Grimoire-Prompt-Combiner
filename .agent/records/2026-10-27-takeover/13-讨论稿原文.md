## 2. NovelAI Prompt Studio：吸收什么（逐条对照过源码）

许可证 GPL-3.0-only（与 AGPL 兼容）。按你的要求只取**行为规格**、重写代码。以下"它怎么做的"全部有源码位置。

### 2.1 七项能力与真实实现

#### N1 提示词块解析 —— 真正的设计是"三层 + 可逆"

它不是我原以为的一层解析，而是 **文本 → Section → Block → Tag** 三层：

- **切块依据是空行/独立成行的闭合标签**（`</artist>`），不是标点；块内再按随机记号 `__池名__` 二次切分。
- **块类型是启发式打分**：`classifyPromptBlock` 用"逗号项数 ≥20、每项 ≤24 词、汉字 <16、功能词占比 <0.2"判 tags；"汉字 ≥16 或 ≥3 个功能词且占比 ≥30%""句末标点"判 paragraph；`text:` 前缀可强制整段为自然语言。（`src/lib/promptDocument.ts:98-171`）
- **权重语法**：`{}` 每层 ×1.05，`[]` 每层 ÷1.05（**层数带符号，`[]` 记负数**）；同字符重复计数即层数；数字权重 `1.2::…::`。回写时**保留用户原来的括号形态**，不折算成 `1.05::`。（`src/lib/prompt.js:112-134, 239`）
- **编辑不是字符串拼接**：定位最内层 weight wrapper → 只替换数字；共享 wrapper 就拆开重写；重写后再解析逐项比对 `tag/weight/brace_depth`，不一致直接抛 `RangeError`。删除后清 `, ,`、空 `{}`/`[]`。（`promptDocument.ts:412-490, 393`）
- **保真自检**：`serializePromptSection(section) === scope.raw_prompt`，对全库统计失败数；`block_annotations` 只存 `type/translation/displayLabel` 这类重解析后必须存活的元数据。

**吸收判断**：这套"原文一字不改 + 可逆解析 + 编辑后自检"的正确性设计值得完整照抄。启发式分类器可以照搬（阈值公开），也可以让用户手动切换块类型——建议两者都做。

#### N2 版本树 + 分支 —— 核心只有一行判断

数据模型：
```
work_versions(id, work_id, parent_id, number, branch_id, branch_number, snapshot_json, source, created_at)
version_images(id, version_id, project_id, seed, created_at)      -- 多对多
work_branch_names(branch_id, name)
work_sequences(已用最大号，删除不回退) / work_activity / deleted_versions / branch_undo / detached_images_undo
```

**"改旧版自动拉分支"就是这一行**（`electron/versions.js:766`）：

```js
const branchNumber = children.length ? parent.branchNumber + 1 : parent.branchNumber
const branchId = children.length ? id : parent.branchId
```

即：父版本**已有子版本**时，新版本把自己当作分支起点（`branch_id = 自己的 id`，`branch_number +1`）；否则沿用父分支。UI 只渲染"当前这条线"（从末端沿 parent 回溯），在分支起点插一个标记行。

两个配套细节值得抄：
- **同签名不产生空版本**：`versionSignature(project)` 相同且无 operation 时直接复用父版本。
- **删除按子树**：`subtree()` + `deleteSubtree`，删除是软删 + 撤销表，`work_sequences` 不回退。

#### N3 图片 ↔ 版本 —— 多对多，不是"图属于版本"

- `version_images` 是联表：**一张图可以被多个版本、多个作品引用**；卡片用 `WorkRef{workId, role:'origin'|'version', versionId, number}` 表达归属。
- 回收站 = `projects.deleted_at`（不删文件）；"从作品去掉"另立 `detached_images_undo` 记录。
- **删共用图会先问**：`useSharedTrash().ask({ids, refsOf, workId})` → 判定是否被其他作品引用 → 无共用直接删，有共用弹三选一：取消 / 只从这个作品去掉 / 放回收站。（`src/shell/SharedTrash.tsx:26-80`）
- **永久删除必须证明无人引用**：先扣掉 `retainedPaths(id)`（仍被存续版本引用的路径），才删文件，并按差集清孤立 inpaint 遮罩。
- **点图恢复作品**：点卡片 → `work.open` → 已有该 work 的 tab 就复用，否则按 `lastVersion` 或该图所在版本打开；进工作台后版本栏就是完整历史。**注意这是"打开作品"，不是"恢复已删除版本"**（后者走 `branch.restore`）。

#### N4 素材库与"反向引用" —— 你的介绍夸大了一点，它其实没有

- 表：`materials(id, kind:'block'|'character'|'pool', name, uses, payload, created_at)`；排序藏在 payload 的 `_order` 里。
- **"每块记得用在哪张图"并没有真正的反向索引**：只有 `uses` 计数（插入成功 +1）和 `examples: string[]`（**保存那一刻**的当前图 id，只用于卡片缩略图）。之后插到别的图不会追加。
- 真正做反向引用的是 **Vibe**（不是块）：`material.vibes` 遍历图库、读图里嵌入的 Vibe 编码、按 sha256 聚合，**读时现算、不落库**。

**吸收判断**：如果你要"每块 → 用了它的图"的实时反查，得自己加 `asset_usage(asset_id, image_id, used_at, via)`——我们做，能比参考实现更完整。

#### N5 Anlas 成本 + 免费回退 —— 公式完整，但只有接 NAI 才有意义

- 免费判定要**五项同时成立**：无 director 参考图、订阅有效且 `tier>=3`（Opus）、面积 ≤1048576（1024×1024）、步数 ≤28、非 V5 且当月用量为负。
- 公式（来自官方客户端，2026-10-20）：`base = ceil(2.951823174884865e-6·W·H + 5.753298233447344e-7·W·H·steps·(medium?1/1.06521739:1))`；`basePrice = max(2, ceil(base·(sm_dyn&&sm?1.4:sm?1.2:1)·(v5?1.5:1)·img2img强度))`；`vibeExtra = 2·max(0, nVibes-4)`；`precise = 5·nPrecise`；`anlas = (basePrice+vibeExtra+precise)·count + 2·pendingEncodes`。
- 免费预设：竖 832×1216 / 横 1216×832 / 方 1024×1024；横幅按横竖方向挑一个"改回免费尺寸"的按钮；inpaint/outpaint 按面积缩到 ≤1MP。

**判断**：我们**没有 NovelAI 生成**（只有 NAI 图片的元数据解析）。这套公式只有在接入 NAI 官方 API 后才有价值 → P3。

#### N6 词典翻译 —— 数据是 GPLv3 派生物，不要直接搬

- 内置词典来自 DanbooruSearchOnline（DSO）固定 commit，52,475 条、2.1MB，生成物 `dso-dictionary.json` 是 **GPLv3 数据派生**；仓库里 `third_party/DanbooruSearchOnline/` 随附 GPLv3 全文。
- 翻译入口是**四级回落**：本地缓存 → DSO 内置 → Danbooru 在线（可失败）→ 规则 → 仅在配置了 AI 时调模型；结果写回缓存。
- AI 两条路：ChatGPT 账号走 OIDC+PKCE + **Responses API + SSE**（system 折成 `instructions`，`store:false`）；API Key 走 `POST {baseUrl}/chat/completions`（强制 HTTPS，仅 localhost 允许 HTTP）。System Prompt 统一是"任务 + 约束 + JSON 输出契约"，user 只放 JSON 数据。

**判断**：我们的标签库已有 4000+ 中英对照，**不需要 DSO**（也不该引入 GPLv3 数据）。真正值得抄的是"AI 整理提示词"的 prompt 结构（JSON 契约 + 硬约束）。

#### N7 Agent 入口 —— 协议比功能更值钱

- CLI `nai-studio`：**202 条命令，其中 119 条 `uiOnly`，Agent 可见约 83 条**（`generate.confirm/cancel/stop/retry`、`settings.*`、`account.*` 对 Agent 全部不可见）。
- 传输：**本地 socket / 命名管道 + token**，一行 JSON 请求/响应，32MB、120s 上限；`connection.json` 里的端点必须是 `\\.\pipe\nai-studio-…` 或 userData 下的路径——注释写明"discovery 是本地文件系统能力，永远不是 host/port"。
- 安装：Unix `~/.local/bin/nai-studio`，Windows 写 `nai-studio.cmd`（`ELECTRON_RUN_AS_NODE=1` 跑 Electron 内置 Node）；Skill 装到 `~/.claude/skills/nai-studio/SKILL.md` 与 `~/.codex/skills/nai-studio/SKILL.md`，用**字节比对**判 installed/outdated。
- **四道护栏全是机制，不是文案**：
  1. 版本记 `source:'user'|'agent'`，UI 给 agent 版本打标；
  2. 只有用户任务完成时才切换舞台（`job.source === 'user' && job.completed === 0`），**Agent 任务只写版本、不动 `tab.versionId`**；
  3. `expectedRevision` 乐观锁 + `workbench.editing` 编辑锁：用户正在编辑的 scope/block，Agent 的写操作直接 `conflict`；Agent 每次写另存 undo（上限 100 条）；
  4. `agentMode:'confirm'|'direct'` + 每日 `dailyLimit`（官方按 Anlas、中转按张数），**`generate.confirm` 是 uiOnly，Agent 永远拿不到确认权**。

**判断**：这套协议值得作为一个独立的"Grimoire CLI + Skill"设计目标，但它是**安全面最大**的一块，建议放在 M2/M3 之后。

### 2.2 顺序建议

**N1 块解析 → N2 版本树 → N3 图↔版本 → N4 素材（含真正的 usage 表）→ N6 的 prompt 结构 → N7 协议 → N5/N8（取决于是否接 NAI API）**

理由：N1/N2 是数据底座；N3/N4 是它们的结果；N6 只借 prompt 契约；N7 是安全面最大的独立工程；N5/N8 需要新外部服务。

### 2.3 重实现的最小数据模型（建议）

```
image(id, name, path, thumb_path, content_sha256, width, height, deleted_at NULL, prompt_fingerprint, origin)
work(id, name, origin_snapshot, saved, created_at, last_used_at, last_version_id)
version(id, work_id, parent_id, number UNIQUE(work_id,number), branch_id, branch_number,
        snapshot, source 'user'|'agent', operation NULL, created_at)
branch_name(branch_id, name)
version_image(id, version_id, image_id, seed, variant NULL, sort)
asset(id, kind, name, payload, order, uses, examples, created_at)
asset_usage(asset_id, image_id, used_at, via)     -- 参考实现没有，我们补
tag_dict(tag, display_tag, translation, category, translation_source, updated_at)
```

不变量：`parent_id`/`branch_id` 必须同 `work`；`branch_id === id && branch_number > 0` 即分支起点；**原文 raw 是唯一权威**，Tag 行与 `block_annotations` 都可重算；所有编辑入口必须带 `expected_revision` + 编辑锁。

## 4. ComfyUI：连接工具 + 网页面板

### 4.1 现状与一个发现

我们已有 810 行（client / quick-workflow / workflow.core / ipc / ComfyUIPanel）。而 **Cherry 源里有一套完整得多的实现**：`comfyuiTransport`（554 行，含轮询/取消）、**`uiToApiPrompt`（882 行，把 ComfyUI 的 UI 格式工作流转成 API 格式）**、workflow discovery、http。这正好补上我们最弱的"任意工作流导入"——**优先 ADAPTED 它，比继续维护自己的节点绑定更通用**。

### 4.2 网页面板的三种实现

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| `<iframe>` | 零新权限；随面板拖拽/缩放/弹出天然工作；和画布面板同一套路 | 跨域读不到 guest DOM；受页面 CSP `frame-src` 限制；极少数自定义节点若判断 `window.top` 会异常 | **先做** |
| `<webview>` | 可注入、可控导航 | 要开 `webviewTag`，等于给渲染进程一个受控浏览器；官方不推荐 | 不用 |
| `WebContentsView` | 权限/导航/会话分区最干净 | 必须手动同步 bounds（拖拽/缩放/tab/浮动/弹出/最大化），z-order 与 DOM 面板混排麻烦 | 回退方案 |

建议：**iframe 先行**，默认 `http://127.0.0.1:8188`，面板给"系统浏览器打开/重载"；实测某常用节点跑不动再升级 `WebContentsView`。

### 4.3 连接工具清单（与面板解耦）

1. 端点管理（本机/局域网/远程）+ 健康检查 + 版本探测（`/system_stats`）。
2. 队列查看/取消（`/queue`）。
3. 能力发现（`/object_info`：节点与模型清单）→ 替掉现在硬编码的 sdxl/krea2/anima。
4. 工作流（`/userdata?dir=workflows` 列出用户已存工作流 → 一键导入；配合 `uiToApiPrompt` 支持 UI 格式）。
5. 提交 + 取回（`/prompt` → `/history` → `/view`），结果写进图片库。
6. 错误分级：连不上 / 工作流无效 / 节点缺模型 / 执行报错。

### 4.4 安全边界

- guest 用独立 session partition；禁 `nodeIntegration`、禁 `webviewTag`（iframe 天然满足）。
- 只允许 `127.0.0.1`/`localhost`/用户显式添加的地址。
- 面板不做地址栏（它不是浏览器），只提供端点选择。

### 4.5 与 Agent 的关系

ComfyUI 生成会成为 Tool Registry 的一个域（`image.generate`），必须走权限策略（有成本），与 M2.3 的 approval 链路复用。

### 7.3 0021 外观设置 / 0072 快捷面板

- **0021 外观**：样式可以借，但**放在主应用设置里**，不放进 Agent 窗口。
- **0072 快捷面板**：做成我们自己的**命令面板**（一个键唤出、搜索、回车执行），并且**与 Agent 共用同一个工具注册表**——人点按钮和 Agent 调工具走同一条路。

### 7.4 工具注册表：把功能做成工具（回答「这样好不好」）

**方向对，但要加五条约束，否则会出现「工具很多、token 更贵」的反效果。**

成本真相：每个工具的**名字 + 描述 + 参数结构**都会进入模型上下文；30 个工具按每个约 70–90 个标记估算，每轮就要 **2000+ 标记**，比很多对话正文还贵。所以：

1. **按域分组、按需装载**：提示词 / 标签 / 图片 / 画布 / 工作区 / 设置 / MCP / 任务，共 8 组；聊天页只装提示词+标签（约 8–10 个工具），Agent 页装全量。分组后单轮工具开销可压到 600 标记左右。
2. **工具粒度 = 用户会说的一句话**，不是 API 函数。例如「把当前提示词存成素材」是一个工具，而不是 assets.create + assets.addTag + assets.linkImage 三个。
3. **返回摘要 + 句柄**：查图返回「20 张，id 列表 + 缩略图 id」，绝不返回图片数据本体；大结果分页，默认 20 条。
4. **写操作两段式**：先 preview 返回「将要改什么」（差异），再 apply；危险工具（删除/执行命令/改设置/批量）必须走权限确认，不能靠模型自觉。
5. **命令面板复用同一注册表**：UI 调用 = Agent 调用 = 同一条实现，避免「界面一套、Agent 一套」的双份维护。

这套东西现在**已经有骨架**：grimoire-tools.ts + 工具注册表 + 权限策略 + 能力账本。缺的是「按域分组装载」和「preview/apply 两段式」。

### 7.8 设置面与视觉定稿（2026-10-27 第三轮）

**设置面**：现有 SettingsWindow 是 900x680 浮窗，用户认为不够大。目标形态 = **占满整个窗口的设置标签页**（左侧分类栏 + 右侧分组卡片），与 Cherry 的做法一致；同时保留「在独立窗口打开」作为可选入口（同一路由可被弹出窗口托管，不写第二份实现）。

**视觉必须二改，不能像套壳**：用户明确——用 Cherry 是因为上一版自研 UI 太丑、覆盖不全；但最终外观要是「Cherry 风格 + 我们自己的设计」，让别人看出是二改而非照抄。

落点（按优先级）：
1. **设计令牌层**：颜色、圆角、间距、阴影、字号、动效统一成一套变量，覆盖到 Cherry 的样式变量上；**不修改 vendor 源码**。
2. **品牌层**：产品名、图标、关于页、窗口标题、空状态插画、启动画面全部换掉。
3. **密度层**：行高、卡片内边距、表格密度按我们的信息量调（Cherry 偏疏，我们偏密）。
4. **组件层**：按钮形状、开关样式、标签样式、对话框圆角与遮罩统一。
5. **布局层**：左侧栏结构、导航语义、页头与面包屑按我们的信息架构重排。
6. **图标层**：统一图标族与线宽（不允许两套图标混用）。
7. **文案层**：术语统一（提示词/标签/素材/作品/版本/会话/智能体）。
8. **动效层**：统一时长与缓动，禁止逐页自定义。

**顺序要求**：先把设计令牌与设置壳定下来，再做 NovelAI 与 ComfyUI 的新界面——否则新页面会按旧风格做一遍，之后还得返工。

**全应用统一**：分三步——(a) 设计令牌与组件基线；(b) 新页面一律按基线做；(c) 老页面在每次因功能需要触及时顺手改，不做一次性全量翻新（除非用户要求）。设置面 + 聊天/Agent 面先做，因为它们是门面。
### 7.9 面板化设置与主题桥（2026-10-27 第四轮）

**设置 = 一个普通面板**：默认在主窗口里以整页标签打开；**双击面板标题 / 点按钮可独立成窗口**；独立前后自动保存与同步。

机制事实（已读源码）：
- 独立窗口走 workspace.openPopout，是**另一个渲染进程**，面板会重新挂载并从共享的工作区文档里恢复；因此状态必须存在 store/数据库里，不能放在组件内部 state。
- 设置写入已通过 data:refresh 广播到所有窗口（settings.ipc.ts:71），同步链路已存在。
- 弹出窗口目前没有 show:false + 背景色 + ready-to-show，会白闪一下——列入 M1.5 修复。

**防闪烁三件事**：窗口背景色取当前主题底色；内容就绪后再显示；原窗口先保留占位块，等弹出窗口 ready 再移除（避免布局跳变）。

**主题桥**：我们的主题是 data-theme + --color-* 变量 + 色轮自定义主色（已有）。Cherry 用的是另一套变量（--color-background / foreground / card / border / brand-50…950 / accent，深色靠 .dark 类）。

映射表（我们 → Cherry）：

| 我们 | Cherry |
|---|---|
| --color-bg-primary | --color-background |
| --color-bg-secondary | --color-card |
| --color-bg-tertiary | --color-muted |
| --color-text-primary | --color-foreground |
| --color-text-secondary | --color-muted-foreground |
| --color-border | --color-border |
| --color-accent | --color-brand-500 + --color-accent |
| 由主色算出的深浅阶 | --color-brand-50…950 |
| 深色模式 | 在 html 上加 .dark 类 |

**二开顺序（用户明确要求）**：先把 Cherry 真页面完整挂上（框架可见），再在外层做皮肤与改造；**不允许用简易组件替换源页面**。每一块未接线的功能必须在界面上明确写「未接线」，让进度看得见。

**哪几层最影响「像不像 Cherry」**：经验上颜色只占三成，**密度、布局、品牌、文案**占七成。所以 M1.5 的重点不是换色，而是：更紧的行高与卡片内边距、我们自己的导航结构、产品名与图标、术语统一。
